# 焦段统计：调研与首版设计

调研日期：2026-09-27。2026-09-28 已继续实现原生应用首版：接入文件夹扫描、访问书签、ImageIO 元数据和 PhotoKit 授权/相簿/资源读取；另保留独立合成数据预览。文件夹功能已实测，真实 PhotoKit 图库流程尚未端到端验证。下文保留设计决策和后续建议，实际能力与验证边界以 README 和 validation.md 为准。

## 2. 现有本地工具：保留与调整

已阅读原本地工具 `photo_tools/tools/focal-length-statistics` 下的 README、grouping.py、cli.py 和分组测试。

保留标准焦段序列：14、16、20、24、28、35、40、50、70、85、105、135、200、300、400、600 mm。

保留比例距离归类：对实测焦距 `f`，选择使 `max(f/a, a/f)` 最小的标准焦段 `a`；距离相同取较小焦段。49、50、51 → 50 mm，33 → 35 mm。相邻锚点的分界是几何均值；24 和 28 mm 的分界约为 25.92 mm。精确模式保留原工具的 1 mm 四舍五入规则，名称旁明确说明分组精度。

建议改进三处：

1. **百分比分母透明。** 旧工具分母是“含 EXIF 的图片数”。新看板建议使用“当前范围内成功读取的照片数”，包含无 EXIF 的 PNG 等，并单列“焦段缺失 / 镜头未知”。例如 1,200 张中 1,140 张有焦段，应同时显示 95.0% 覆盖率与 60 张缺失。损坏、无权限、云端未下载的照片另列为未分析，不混进元数据缺失。原型采用这个新口径。
2. **等效焦距回退须核实。** 旧代码直接接受 ExifTool 的数值 `FocalLength35efl`。本机 ExifTool 13.55 的 `Exif.pm:4709–4720` 显示：该字段在缺少 `ScaleFactor35efl` 时会乘以 1，返回实际焦距。因此不能仅凭字段名认定它是可靠的等效焦距。新实现应优先标准等效字段；回退计算要求有效的换算依据，并标记“推算”；依据不足就记为等效焦距缺失。上游实现见 [ExifTool Exif.pm](https://github.com/exiftool/exiftool/blob/master/lib/Image/ExifTool/Exif.pm)。
3. **边界值不误导。** 旧算法会把小于 14 / 大于 600 的值压到端点。新方案在标准序列范围外保留原值，尤其实际手机焦距常小于 14 mm。原型已加入这个规则，避免把 6.86 mm 显示成 14 mm。

首屏可只显示 Top 5 焦段，并提供全部列表；不暗示这五组加起来等于 100%。若以后继承“低于 5% 隐藏”的规则，应把隐藏组总数和总占比明确呈现。

## 3. 来源、权限与文件计数

### 本地文件夹

第一次使用通过系统文件夹选择器授权，保存只读 security-scoped bookmark。后续启动恢复书签；每次扫描正确开始与结束访问。书签陈旧时尝试更新，解析失败、权限撤销或磁盘离线时给出对应提示，不在每次启动重复弹窗。新选一个未授权文件夹仍需选择器授权。[Apple：沙盒文件访问与持久书签](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)

两种范围：当前文件夹仅扫描直接子文件；递归模式扫描所有普通子文件夹。默认跳过符号链接、隐藏文件和包目录，不把 `.photoslibrary` 当普通目录递归遍历。大小写不敏感识别 JPG/JPEG、PNG、HEIC/HEIF，内容格式检查失败单列。PNG 支持读取，不代表必然有相机 EXIF。

文件夹模式按独立静态照片文件计数；默认不进行内容去重。同一照片的 JPEG 与 HEIC 两份导出文件会算两张，这一点在帮助里说明。Live Photo 的 MOV 配对文件不参与计数，只统计静态图像，因此通常一对为一张；若需要展示 Live Photo 数量，再用内容标识符配对，不能仅凭同名认定。

### Apple 相册

使用 PhotoKit；在用户第一次选择 Apple 相册来源时请求权限，之后先检查系统授权状态。拒绝后提供前往设置的操作，不循环申请。PhotoKit 的读取授权使用 `.readWrite` 访问级别（没有通用 `.readOnly` 级别），应用本身只读取，不执行图库修改。[Apple：PHPhotoLibrary](https://developer.apple.com/documentation/photos/phphotolibrary)

相册模式显示“所有照片 / 选择相簿”，不显示文件夹递归开关；相簿不是磁盘目录。跨相簿合并时按 `PHAsset.localIdentifier` 去重。一个 Live Photo 资产只计一次，读取静态资源；原图与编辑资源也不重复计数。图库中的 RAW 配对优先使用支持的静态资源，只有 RAW 的资产在首版列为不支持。[Apple：PHAssetResource](https://developer.apple.com/documentation/photos/phassetresource)

首版默认只分析本机可用资源。iCloud 中未下载的原件单列“待下载”，允许用户主动开启下载后重试；不能把它们报为没有 EXIF。`isNetworkAccessAllowed` 控制 Photos 是否下载原件。PhotoKit 获取图片数据可能读取完整的压缩图片资源，因此不能承诺整个相册扫描只读少量 EXIF 字节。[Apple：网络访问与云端图片](https://developer.apple.com/documentation/photos/phimagerequestoptions/isnetworkaccessallowed)

权限体验的前提是固定的 Bundle ID 与稳定的签名身份。开发过程中更换身份和用户撤销权限可能触发重新授权，因此产品文案使用“记住访问权限”，不承诺永不重新授权。

## 4. 统计模型

镜头型号与焦段是两个独立维度：24–70 GM II 在 35 mm 拍摄，仍属于 24–70 GM II 的镜头组，不得合并进 35 GM。

镜头识别优先标准 `LensMake` + `LensModel`，有需要再使用已核实的厂商镜头 ID / ExifTool 解析；只清理空格、统一明确的同型号别名。保留原始型号以便检查，不能仅凭 24–70、F2.8 等范围猜出具体型号。不同代、不同厂商、增距镜组合不得模糊合并。“识别镜头数”实际是不同镜头型号数，不能推断用户有几件物理器材。

每张记录保存：来源唯一标识、读取状态、相机型号、镜头原名/规范名、实际焦距、等效焦距及其来源（原始/推算/缺失），以及后续可用的光圈、快门、ISO、拍摄时间。不依赖拍摄时间猜测镜头型号。镜头未知但焦距可用的照片仍进入焦段统计，反之亦然。

默认全画幅等效焦距，便于相机与手机共同比较；切换实际焦距用于观察变焦环位置。筛选镜头后，焦段面板和摘要按筛选后的照片重新计算；镜头列表继续显示整个来源占比，并保留分母说明。

## 5. 看板信息优先级

| 优先级 | 内容 | 能回答的问题 |
| --- | --- | --- |
| 首版必需 | 照片数、可用焦段数/覆盖率、识别镜头型号数 | 这次统计覆盖了多少照片？ |
| 首版必需 | 焦段数量与占比、标准/精确、等效/实际切换 | 我最常用什么视角？ |
| 首版必需 | 镜头数量与占比、点击联动焦段 | 我的 35 mm 主要来自哪支镜头？ |
| 首版必需 | 未识别镜头、缺失焦距、读取失败、云端待下载 | 结果有多少未知？ |
| 首版实用 | 机身筛选、拍摄日期范围、CSV 导出 | 单次旅行、单台相机是什么情况？ |
| 后续推荐 | 变焦镜头广端/长端使用率 | 是经常顶着 24 / 70 mm 拍，还是居中使用？ |
| 后续推荐 | 镜头 × 光圈分布 | 35 GM 是否经常使用大光圈？ |
| 后续推荐 | 两个文件夹 / 两段时间对比 | 拍摄习惯有变化吗？ |
| 后续可选 | ISO、快门分布；仅收藏照片统计 | 拍摄环境和自己偏爱的照片有什么区别？ |

端点使用率要根据镜头的真实物理焦距范围及明确容差计算，不能拿等效焦距直接比较标称镜头端点。定焦/变焦分类也要有可靠镜头范围信息。收藏占比不能称为“出片率”；拍摄数量多不能直接推荐购买或出售器材。

## 6. 界面方案

遵循 `mac-photo-app-ui`：浅冷灰背景、白色细边卡片、蓝灰主操作、系统字体、12 pt 卡片圆角。顶部居中光圈符号、标题与一句用途；左栏 260 pt 放“1 照片来源”和“2 统计方式”；右侧为三项摘要、焦段与镜头两个面板、简短观察。底部独立进度条，剩余时间固定在右侧。高级选项收起，结果与左侧分别滚动。

默认内容尺寸 1180 × 830，最小 980 × 700。选择镜头后突出该项并显示“显示全部照片”。停止与失败保留非满进度；扫描时锁定来源与统计设置，停止按钮持续可用。目录中间省略并提供完整路径提示。

应用已实现：来源与范围切换、PhotoKit 相簿选择、标准/精确分组、实际/等效切换、镜头联动、全部焦段展开、CSV 导出、五种任务状态、实时剩余时间、最小窗口预览。演示入口使用独立合成数据，不会申请相册或磁盘权限。开始/停止操作固定在侧栏底部，不随设置滚动。

## 7. 建议的正式版技术路线

当前目录原本为空，没有需要保留的框架。建议沿用原型的 **SwiftUI + AppKit 窗口与系统对话框**，PhotoKit 接入图库，ImageIO 读取标准元数据；统计逻辑独立于 UI，采用批处理后台任务与有界并发。

第一步先做小规模元数据兼容性验证：Sony 24–70 GM II / 35 GM、iPhone HEIC、Live Photo、缺 EXIF 的 PNG、编辑导出 JPEG。只有标准字段无法满足镜头识别时再评估内置 ExifTool，避免要求最终用户安装 Homebrew，同时不先承诺 ImageIO 能识别所有厂商私有字段。包体积、扫描速度、云端图库覆盖率须在真实实现后测量。

正式版建议顺序：

1. 文件夹扫描与分组纯函数测试；读取失败不打断整批，及时停止。
2. 持久书签、稳定身份打包；用合成目录验证关闭重开后的访问。
3. PhotoKit 相簿与资源读取；用隔离测试图库验证 Live Photo、iCloud 状态和权限分支。
4. 镜头识别样本对照、筛选与 CSV；必要时增加元数据缓存。

缓存仅存元数据，按文件标识/修改时间/大小或资产标识/修改时间失效，并包含解析器版本；首次不读取像素缩略图。验证项目包括递归边界、重复计数、未知数据分母、分组边界、零照片、取消/重试、最小尺寸与权限恢复。
